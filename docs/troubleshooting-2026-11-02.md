# 相册网格列表排障实录（2026-11-02）

早上第一版网格可用,一天内多轮修改后"越改越不行"。全部为设备端 UI
(app_album.cc)的应用逻辑回归,服务端与同步层(album_sync.cc)无问题
(81 张照片全部 ≤18KB,manifest 正常)。已修并编译过全部门禁。

## 根因(按影响排序)

### 1. 看图返回网格时模式没设回去(网格"一去不回")
- **现象**:网格里按确定进全屏看图,再按确定回不去——界面停在照片上,
  上/下键还在翻照片,列表等于永远丢失,只能长按退出应用。
- **根因**:`exit_photo_mode()` 的回网格分支只把 `s_grid_render_page`
  置 -1,忘了把 `s_mode` 从 PHOTO 设回 GRID。album_task 只在
  mode==GRID 时才渲染,于是重渲染永远不会发生;按键分发也按 PHOTO 处理。
- **修复**:回网格分支补 `s_mode = GRID`(+ LVGL 失效保持关闭)。
- **教训**:**三态机(STATUS/GRID/PHOTO)的每次转换必须完整落位,
  改"重渲染触发"时先 grep `s_mode` 的全部写点。**

### 2. 网格内每按一次方向键就整页重渲染
- **现象**:同页移动光标也触发白屏闪 + 12 次拉图+解码(约 5 秒),
  翻一格等 5 秒,列表基本不可用。
- **根因**:`grid_move()` 无条件 `s_grid_render_page = -1`(该哨兵同时
  兼任"请求渲染"与"已渲染页号")。而格子间预留 3px 纯黑边距、
  `grid_draw_frame()` 可无损重画选中框,这套机制就是为"同页零成本挪框"
  设计的,但 grid_move 从没走这条路。
- **修复**:同页只擦旧框/画新框(零网络零解码);仅跨页才置 -1 整页渲染。
- **教训**:**"请求渲染"和"页号记录"混用一个变量时,任何触发点都要
  先问:这次操作真的需要整页重画吗?**

### 3. 白闪调试代码留在主路径 + 页眉永久变白
- **现象**:每次进网格/翻页全屏白闪一下;顶部 16px 页眉被闪白后再没人
  重画,一直是白的。
- **根因**:render_grid_page 开头的"白闪验证管线"是调试遗留;白闪覆盖
  整屏(含页眉),而后续只逐格清黑(页眉以下)。
- **修复**:改为整屏清黑(含页眉)一次,随后逐格渐进填充。

### 4. 缩略图列抽样窗口按 280 宽写的(实际照片 240 宽)
- **现象**:缩略图比预期窄(55 列而非 60 列)且不居中。
- **根因**:grid_jpeg_output 列窗口 `ax<20 || ax>=260` 是按 280 宽源图
  写的;管线实际产出 240×320(make_album.py 保证),只能抽到 55 列。
  行窗口(居中抽 70 行)是对的。
- **修复**:窗口改按 `decoder->width/height` 实际计算并夹在面板尺寸内
  (240→列 0..239 恰好 60 列;顺带保证超大图也不会越界写 row[60])。

### 5. 退出竞态:退出后解码还在往面板贴图
- **现象**:退出网格/应用后,状态屏上偶发残留缩略图条纹,LVGL 不会
  主动重画那块区域。
- **根因**:格子解码(拉图约 0.4s)期间模式可能已切走,解码回调仍直推
  面板;ui_show_status 的全屏失效发生在贴图之前就输了。
- **修复**:三处守卫——grid_decode_cell 拉取后、grid_jpeg_output 每解码块、
  album_show_photo 拉取后,发现模式已不是 GRID/PHOTO 即中止并不再贴图。

### 6. 服务端脚本尾巴上的 NameError
- make_album.py 删除总览图(sheet)生成时,最后一行 print 还引用
  `sheet_total` → 每次生成完必抛 NameError(文件已写完,不影响产物,
  但 compose run 退出码非零,极具迷惑性)。已改为不引用该变量。
- **教训**:**删功能要全文搜标识符的残留引用,包括"只打印"的。**

## 附带清理
- 删除死代码 `grid_show_current()`/`enter_stream_ui()`(等待渲染的旧方案
  残留,误导排障)。
- grid_decode_cell 去掉从未使用的 stripe 分配(省 1.9KB 峰值堆)与
  render_grid_page 里重复的琥珀块绘制(统一在 decode 内画一次)。
- album_sync.h 删除已废弃的"服务端拼 sheet_XX.jpg 总览图"设计注释
  (与实现不符,误导后手)。

## 验证
- `bash build.sh` 编译通过;`verify_firmware.py`:布局 PASS、
  **SRAM 首堆区域 75672/73728 PASS**、合并镜像 PASS。
- 真机回归点:进网格自动渲染 → 同页挪框即时 → 跨页渐进重渲染 →
  确定看图 → 确定回网格 → 长按下回状态屏 → 长按上幻灯片。

# 第二轮:网格"黑屏只剩细缝"(当天下午,真根因)

上面第一轮修完后真机表现:列表纯黑,加载 10+ 秒后每格只露出左缘
一条 4px 宽的竖向细缝,像被黑图层盖住。逐层排查:

## 排除项(都是好的)
- 服务端照片:81 张全部 baseline JPEG、≤18KB,manifest 正常;
- 解码链路:把 tjpgd + photo_jpeg_input + 抽样逻辑原样搬到 Mac 上跑,
  jd_prepare/jd_decomp 全过,缩略图内容正确;
- Wi-Fi 省电档:相册已在 BALANCED 名单(app_registry.cc);
- 颜色/任务栈:UI_ACCENT 为琥珀 0xDDB36C;sizeof(JDEC)=240B。

## 真根因:TJpgD 按 16px MCU 块回调,贴图却每块都从格子左缘排起
- **机制**:TJpgD 的输出回调每次只给一个 16×16 块(bitmap 是块的,
  不是整行的)。每块按 1/4 抽样出 4 列,代码把这 4 列画在
  `grid_x + 0..4`——15 个块全部叠在同一位置互相覆盖,只剩最后一块,
  即每格左缘一条 4px 竖缝。全屏看图路径没这个问题:它把块写进
  整幅 stripe 缓冲时用的是 `rectangle->left + x` 绝对列号。
- **修复**:抽样列按 `ax/4` 映射成缩略图列号,记录块内首列
  `first = ax/4`,画在 `grid_x + first`,宽度 = 本块抽样数。
- **本机验证**:harness 模拟每次 draw 落点,断言 60×70 像素
  **恰好覆盖一次、无缺失无重叠**,三张真照片全过。
- **教训**:**本机复现必须连同"落点"一起复现**——第一轮的 harness
  只验证了抽样计算(用 ax/4 正确寻址写缓冲),没验证 draw 的 x 坐标,
  于是这个 bug 从眼皮底下溜走了。回调式 API 的复现要对每个回调参数
  建模,不能想当然"拿到的是整行"。

## 排障工具(固化下来)
- **页眉进度条**:一格一段,加载中一眼可辨(段在走=网络慢,不动=卡死,
  重启=崩溃)。
- **状态屏 detail 行**:照片拉取失败原因直接上屏(本设备无串口日志,
  屏幕是唯一输出口;§4.3 的教训重申:诊断行丢了就只能盲修)。
- 加载耗时预期:在线逐格模式每格约 1s(拉 17KB+解码),整页 12 格
  约 10-12s,属设计成本;同页内导航即时。

# 第三轮:加载提速 + 页眉页码(当天傍晚)

细缝修好后网格可用但整页要 10-12s(12 格 × 拉 17KB 原图 + 全尺寸解码)。

## 提速:服务端预生成缩略图,网格不再拉原图
- **方案**:make_album.py/sh 在生成 240×320 原图的同时,产出
  `thumbs/<name>.jpg`(60×70,对应原图中心 70/80 行,约 2KB)。设备网格
  优先拉缩略图 1:1 解码直贴(sample_step=1);**旧源没有 thumbs/ 时自动
  回退原图 1/4 抽点**(sample_step=4),探测请求不写 detail,不污染状态屏。
- 实测:缩略图最大 2172B(原图约 1/8),解码量 1/16,整页约 2s。
- 抽样逻辑泛化:步长从硬编码 4 改为 context->sample_step,列/行窗口按
  `min(图幅, 面板)` 与步长居中计算;本机 harness 用真实缩略图与原图
  双路径验证覆盖恰好一次。
- **注意**:Dockerfile 是 `COPY make_album.py` 进镜像的——**改脚本必须
  `docker compose build` 再 run 生成**,直接 run 跑的还是旧脚本。

## 页眉页码
- 直推模式下 LVGL 失效已关,没有字体渲染;页码用 3×5 点阵数字放大
  2 倍手工绘制("3/7" 样式),右侧对齐;进度条改 16px/段靠左,互不遮挡。
- 顶部颜色说明:进度条/选中框颜色 = UI_ACCENT = 当前系统主题的强调色
  (CLASSIC 主题为青绿 0x8CF5A6),与全机选中态一致,非相册私有配置。

## 第四轮:相册源零操作化(产品诉求:"照片丢进去就行")

用户不想要"服务端还要跑脚本生成缩略图"的维护动作。方案:**把生成
步骤变成服务的内部行为**——`album_server.py`(tools/album/,Docker 部署)
替换纯静态 http.server:每次请求前按 (mtime,size) 对 src/ 增量同步,
新照片自动转原图+缩略图,删除自动清理,manifest 自动重写;没有变化时
只是一圈 stat,毫秒级。缩略图从"用户要管理的产物"降级为"内部缓存"。
- 部署注意:Dockerfile 是 COPY 脚本进镜像的,改脚本必须
  `docker compose build` 再 `up -d --force-recreate`。
- 全生命周期已测:放入照片 → 清单自动 +1、缩略图自动出现;
  删除 → 自动清理,清单恢复。
- 固件零改动(缩略图优先 + 原图回退的兼容逻辑直接复用)。

## 第五轮:双选中框与翻页体感

- **双框(末页尤甚)**:grid_move 同页挪框是"擦旧框→更新 sel→画新框"
  三步,与渲染收尾的 `grid_draw_frame(s_grid_sel, true)` 在两个任务间
  无互斥——渲染恰好插在中间就会把已擦的旧框画回来,且 s_frame_h/v
  共享缓冲被两任务并发使用还会撕帧。**修复:新增 s_frame_mutex,把
  "读旧 sel→更新→擦旧→画新"与渲染收尾补框串行化。**
- **翻页像没反应**:album_task 轮询 1s,翻页后最长干等 1s 才开始清屏
  再 2s 填满。**修复:轮询降到 150ms(按键后立即清屏+进度条起步),
  且渲染顺序改为从选中格开始(先看到目标位置,其余渐进补)。**
- 连带:末页空格上按确定原来会拉图失败掉回状态屏,改为空格无操作。
- **教训**:跨任务的直推绘制必须有"绘制权"互斥——逻辑上不冲突的
  两段绘制,交错执行也会产生可见脏状态;状态读取要和绘制放进同一
  临界区,否则读到更新前的值就会复画。

## 第六轮:头尾绕圈导致的"卡死在末页"(交互语义修正)

真机反馈:末页按住下键"翻不了页"、往上退时首格出现高亮且双框、
末页往上"动不了"。根因是**头尾循环翻转**的语义与渲染节奏相互放大:
- 末页最后一张再按下 → 绕回首页;首页第一张再按上 → 绕回末页。
  状态在 0↔末页之间弹跳,配合按键连发,每次键击都打断并重启整页
  渲染(屏幕反复清黑、永远填不满),视觉上就是"卡在末页/高亮乱跳"。
- **修复 1(语义)**:按用户预期改为**到头停住**——abs_idx 钳制在
  [0, count-1],末页尾部往下不动、末页顶部往上正常翻回上一页。
- **修复 2(防抖)**:跨页导航记录 s_nav_last_us,渲染等停键 200ms
  再启动,按住键不再反复打断渲染。
- **修复 3**:渲染起点改为进入时快照(start_cell),不再每格重读
  s_grid_sel——中途挪框不会导致格子被跳过或重复渲染。
- **教训**:"循环浏览"在逐页异步渲染的界面上是反模式:边界弹跳 ×
  渲染重启 = 不可预测的中间态。**列表导航先问用户预期(停住还是绕圈),
  异步渲染的界面默认选"停住"。**

## 第七轮:照片圆角展示(样式统一)

产品要求:相册照片与设备 UI 的圆角风格一致(速算24 卡片 4px/面板 6px)。
- 实现:`pixel_rounded_off(x,y,w,h,r)` 纯函数遮罩——中部列/行永不裁,
  四角按 (r-x)²+(r-y)²>r² 判定;图任一边 < 2r 不裁(防退化)。
  网格缩略图 r=4(遮罩像素不画、露黑底);全屏 r=6(遮罩像素写黑,
  因为全屏后面板底色未知,必须显式覆盖)。
- 第一版遮罩用 (r-1-x)² 偏移,r=4 时每角只裁 1 像素(肉眼不可见)——
  本机点阵图验证形状后改为 r-x 偏移(每角 8/14 像素,四角严格对称)。
- 教训重申:**像素级效果先在主机上打印点阵验证再上设备**,省一轮烧录;
  另:构建失败的 && 链会继续烧录旧产物——烧录前必须确认"build complete"
  真的出现(本次踩到,靠应用体积差异识破)。

## 第八轮:快速连按上下键崩溃重启(面板单写者重构)

真机反馈:网格里连续快按上/下几次就 panic 重启(CONFIG_ESP_SYSTEM_
PANIC=PRINT_REBOOT,串口看不到打印)。
- **排查**:排除异步 DMA(tjpgd 直推若异步,缩略图早花了——实际显示
  正确,说明 tx_color 同步);排除输入任务栈(8KB 且 grid_move 很小);
  确认相册在按键音名单(feedback_allowed)——**每次按键都触发一次音效
  资源分配**,而按键任务同时在画面板、渲染任务同时在拉图+解码+贴图,
  三路并发挤 ~25KB 的小堆,快速连按极易耗尽 panic。
- **修复(结构性):面板单写者**。input 任务只改状态(零分配零画屏):
  同页挪框 → s_frame_dirty 请求;看图/翻页 → s_photo_req_index 请求。
  album_task 是唯一画屏者:消费请求(enter_photo_now/flip_to)、渲染
  页(渲染循环间隙顺带应用挪框、有看图请求立即让位)、推幻灯片。
  另:album_task 栈 6144→8192;photo_jpeg_output 补模式守卫(与网格
  输出对称);幻灯片残留标志在进图时清掉。
- **教训**:**小内存设备上,"谁能画屏"要像"谁能拿锁"一样纪律化**。
  多任务各自直推面板 + 各自分配,崩溃点会漂移(有时是音效,有时是
  HTTP,有时是解码),逐个补丁永远补不完——收敛到单写者/单分配路径
  才是根治。

## 第九轮:单写者版卡在"正在获取照片列表"(内存账教训)

第八轮顺手把 album_task 栈 6144→8192(+2KB 堆),结果设备必现卡死在
清单获取(RUNNING 永不结束)。服务端正常(响应 9ms,日志可见设备
拿到 manifest 200 后再无下文)。
- **根因**:进相册瞬间堆分配 = 两任务栈(8192+6144)+ 清单缓冲 4KB
  + HTTP 客户端 ~2.5KB,把 ~21KB 空闲堆顶穿;同步任务内部某个未检查
  的分配拿到 NULL 后挂死,状态停在 RUNNING。上一版(栈 6144)恰好
  差 2KB 没爆——**"多退少补"的 2KB 就是能用与不能用的分界**。
- **修复**:栈退回 6144(防崩溃靠的是单写者重构,不靠栈);
  RUNNING 状态行加自检信息:"正在获取照片列表 Ns 堆XKB"——秒数
  一直涨=任务挂死,堆数字逼近 0=内存耗尽,排障不再靠猜。
- **教训**:**这台设备加任何常驻分配前先算总账(任务栈也是堆!),
  临界余量只有 KB 级;顺手优化尺寸的改动必须单独验证启动路径。**

## 第十轮:孤儿高亮框 + 页眉改版

- **孤儿高亮框**(选图后右下角残留):帧状态三件套
  (s_frame_prev_sel/s_grid_sel/s_frame_dirty)在 input 写、album_task
  读之间无锁,并发时可能读到"混合的新旧对",按错误格子擦框,某个
  高亮框永远擦不掉。当初注释写"最多闪一次,下一轮 dirty 自愈"——
  **自愈假设错误**:下一轮的 prev 就是那个混合值,擦的还是错格子。
  修复:三件套纳入 s_photo_mutex 配对读写。
- **页眉改版**:进度条改细(16×4px 顶行);下行左侧电池图标+百分比
  点阵、右侧页码点阵——直推模式下没有字体/控件,全部手工点阵。
- **教训**:**"会自愈"是假设不是验证**——注释里写自愈之前先推演
  下一个周期的输入是什么,本例下一轮的擦除目标恰恰继承了脏值。

## 第十一轮:长按确定(退出应用)崩溃 + 页码放大

- **长按确定退出崩溃**:退出时渲染任务可能正卡在一次拉取里(HTTP
  超时 8s),握着十几 KB 堆不放;桌面切换紧接着分配,两头一挤 OOM。
  album_sync_cancel 的 s_cancel 标志**从第一版起就没被任何读取点接
  过**——是个空转的开关。修复:fetch_to_heap/http_get_mem 入口与
  读循环都检查 s_cancel(退出瞬间打断);prepare_stop 等 album_task
  退出(上限 1s,通常 <100ms)再放行切换;渲染循环加 !s_active 中止。
- **页码**:电池显示按需求撤掉;页码点阵 2 倍→3 倍放大(9×15 占满
  页眉),清晰可读。
- **教训**:**"取消"机制必须闭环**——有设置无读取的 cancel 标志比
  没有更糟,它给人"已经处理了退出"的错觉。退出路径要在真机上专门
  测:正在加载时退出是最容易暴露资源残留的时刻。

## 第十二轮:右缘高亮残留(照片取证 + 复合状态竞态)

真机照片做像素取证:网格换算(以亮度带定位 3×4 网格,比例 ~2.5px/
屏幕像素)后,确认**几乎每个格子的右边距(x≈75-79)都有强调色竖条,
高度不一**;颜色与页眉界面色同族(拍照偏色后仍可区分于照片内容绿);
服务端 81 张缩略图全部 60×70(排除服务端)。
- **根因:复合状态竞态。**上一轮只给"挪框三件套"加了锁,但还剩两处
  读写没有配对:① grid_move 跨页分支写(页+格)未加锁;② 渲染收尾
  画选中框时,读 s_grid_page 与 s_grid_sel 是**两条独立指令**——中间
  被按键更新后,就会把"别页的选中格"画在当前页上,产生**无人认领、
  无人擦除的孤儿框**(整框四边,右缘在照片里最易辨识)。单核不保证
  复合读的原子性,锁才保证。
- **修复**:复合状态(页+格)的全部读写在 s_photo_mutex 内配对完成
  (跨页分支、渲染收尾补框)。页码按用户要求换 5×7 经典点阵
  (1px 宽笔画 × 2px 高,细体)。
- **教训**:**锁要按"状态组"设计而不是按"函数"打补丁**——同一组
  复合状态的每一处读和每一处写都必须进同一把锁,漏一处,竞态就还在。

## 第十三轮:"孤儿框"真因——失败标记长得像选中框

用户反馈正常速度上下切换就有"孤儿框"。两步定位:
1. **主机模拟器**(/tmp/grid_sim.py):复刻 grid_move/apply/render/
   收尾的锁语义与节拍,3000 组正常速度随机序列**全部无孤儿**——
   证明框逻辑本身正确,问题在模拟没建模的东西。
2. 重新审视照片证据 + 代码:**格子解码失败时画"满格强调色块"当
   错误标记(调试期设计)——看完全屏照片(18KB 级缓冲反复进退出)
   堆被切碎,返回网格重渲染时排最后的格子(右下角!)分配 4KB 解码
   工作缓冲失败 → 满格色块**。所谓"残留高亮"根本不是选中框,
   是失败标记与选中框撞了脸。
- **修复**:① work 缓冲改为整页渲染只分配一次(12 次→1 次,碎片
  概率大降;分配失败则整页黑屏 150ms 后重试,不逐格标块);
  ② 失败标记改为格子左上角 24×3px 小条,绝无可能与选中框混淆。
- **教训**:**调试用的可视化标记要和正常 UI 元素拉开视觉差距**
  (尺寸/形状/位置至少一项悬殊),否则它一旦出现就会被当成 UI bug,
  把排障带偏一整天。

## 第十四轮:孤儿框真根因——draw_bitmap 是异步排队传输(源码实锤)

用户确认当前固件仍有孤儿框。状态机模拟已排除逻辑层,转向驱动层:
查 ESP-IDF esp_lcd SPI 源码,`esp_lcd_panel_io_tx_color` 用
**`spi_device_queue_trans`(排队即返回,异步 DMA)**——draw_bitmap
返回时传输还没发生,源缓冲必须保持不变。
- **机制**:grid_draw_frame 把框边内容写在两个**静态缓冲**里排队 4 笔
  传输;apply_frame_move"擦旧框(黑)→画新框(琥珀)"会立刻把同一对
  缓冲重填成琥珀——在途的"擦除"DMA 读到的是重填后的琥珀,把擦除
  画成了孤儿高亮框。DMA 预取与 CPU 重填的竞争还解释了"只有下半段
  是高亮色"的形状(上半段已按黑色发送)。
- **旁证**:全屏路径早就在用 `tx_param(0x00)` 当屏障(color_pending
  逻辑),所以全屏从不花屏;BSP 的 bsp_display_fill 同款并注释
  "等待所有已排队的 SPI DMA 传输完全落地"。缩略图安全是因为切片间
  有解码耗时(~100µs)远大于传输(~3µs)。
- **修复**:grid_draw_frame 末尾与页码绘制后发 `tx_param(0x00, NULL, 0)`
  屏障(polling 命令强制先排空队列,ST7789 的 0x00 = NOP,无副作用)。
- **教训**:**换直接面板直推时先读驱动源码确认同步语义**——"无回调
  就同步"是 BSP 注释的想当然,实测源码是 queue_trans 异步。凡静态/
  栈缓冲 + 异步写,"写完立刻改缓冲"的模式都要加屏障或双缓冲。

## 第十五轮:加载中长按确定退出 → 整机冻结(退出顺序违抗单写者)

真机:网格加载中长按确定(退出到桌面),界面冻结不动。
- **根因**:第十一轮给 prepare_stop 加的"等任务退出"之前先调了
  ui_show_status()——恢复 LVGL 失效会让 LVGL 任务**立刻渲染状态屏**,
  与仍在收尾直推的 album_task(卡在 ≤8s 的阻塞网络调用里)形成两个
  面板写者。LVGL 的 flush 完成信号经由同一 esp_lcd IO 的
  on_color_trans_done 回调应答,相册在途传输的完成会"代答"LVGL 等
  的那笔信号;LVGL 自己真正的传输完成时反而无人应答 → 抱着 LVGL 锁
  永久等待 → input_task 卡在 bsp_lvgl_lock(-1) → 全机冻结。
  加载中退出最容易触发(直推最密集,代答概率最大)。
- **修复**:prepare_stop 顺序调整为 **cancel → 等任务退出(≤2s)→ 再
  ui_show_status**。全程维持面板单写者纪律——退出路径的每一步都要
  遵守它,而不是只在正常运行时遵守。
- **教训**:**单写者纪律覆盖退出路径**。上一轮修崩溃时引入的
  ui_show_status 提前调用,就是退出路径上的第二个写者;每次给退出
  流程加步骤,都要重新检查"此刻面板上有几个写者、信号归谁"。

## 第十六轮:重进相册永远"正在获取 0s 堆87KB"(粘滞会话状态)

真机:再次进入相册,永远停在"正在获取照片列表 0s",堆 87KB 高挂
(说明没有任何东西在拉清单)。
- **根因**(第十五轮退出顺序修复的连带暴露):退出时的 cancel 要等旧
  清单任务走出阻塞网络调用(最长 ~8s)才生效,期间 `s_status` 停在
  RUNNING;在这个窗口内重新进入相册,`album_sync_refresh_start` 的
  防御检查"RUNNING 就拒绝"直接返回——不重置 cancel、不建新任务。
  于是没有任务拉清单(堆高挂),状态永远是 RUNNING,"正在获取 0s"
  (running_since 未初始化为 -1 时秒数恒为 0)。
- **修复**:refresh_start 改为"先叫停、等旧任务 ≤1s 退场,再开新任务";
  旧任务实在堵在系统调用里就本次拒绝(它退场时置 NET_FAIL,下次进入
  正常刷新)。
- **教训**:**"防御性拒绝"要看状态的生命周期**——RUNNING 是会话态,
  会被异常退出粘滞;入口处的拒绝必须配套"排空旧会话",否则一次异常
  退出就永久锁死后续所有会话。三个观测(0s 不变/堆高挂/永不转换)
  联立才锁定真因——单看哪一个都会引向死路。

## 第十七轮:相册内"返回"手势卡死(同一漏洞的第二个入口)

真机:网格里长按下键(返回状态屏),整机冻结。
- **根因**:与第十五轮退出卡死完全同机制、不同入口——on_key 的
  "回状态屏"直接调 ui_show_status():恢复 LVGL 失效让屏幕系统立刻
  渲染,而 album_task 还在网格渲染循环里(要等当前格子的拉取/解码
  走完才走到中止检查,~0.5-1s),两个面板写者并发 → flush 完成信号
  被代答 → LVGL 抱锁睡死。第十五轮只修了 prepare_stop 入口,应用内
  部的返回入口漏了。
- **修复(纪律化,不再逐点打补丁)**:
  ① `s_panel_busy` 原子标记 + PanelBusyGuard RAII——render_grid_page
  与 album_show_photo 全程标记;
  ② ui_show_status 统一改为:先置 STATUS(模式守卫即刻中止新绘制)→
  非 album_task 调用时等 `s_panel_busy` 落空(≤2s,超时放行安全:残余
  绘制全有模式守卫)→ 再恢复 LVGL;album_task 自身调用跳过等待(等
  自己=死锁);
  ③ 返回键路径先 album_sync_cancel 打断在途拉取,缩短等待。
- **教训**:**修复"并发写面板"这类结构性问题,要按机制修(统一
  交还纪律)而不是按入口修(每个按键路径各补一刀)**——第 15/17 轮

## 第二十轮:冻结真因——USB 控制台阻塞式写入(帧指针调用栈实锤)

诊断固件(帧指针版)部署后用户复现"正在获取卡死",取证链全部命中:
- **WDT 转储首次带真实调用栈**(帧指针生效);'F' 栈扫描同时命中。
- **album_task**:blocked 在 `lock_acquire_generic`(newlib 锁)——
  hwm=2596(无栈溢出),state=2。
- **sys_mon**:blocked 在 `_svfprintf_r` → console 写——**它持着
  newlib stdio 锁**卡在打印里。
- **闭环**:某任务的 ESP_LOG 需要写 console → **USB-CDC 阻塞式写入在
  主机端不读取时永久挂起**(CDC 缓冲满 + 主机不排空)→ 该任务持
  newlib 锁睡死 → 所有要打印/分配的任务排队 → 按锁的归属不同,
  表现成"列表卡死/正在获取/整机冻结"各种形态。
- **为什么总在调试时发生**:电脑侧采集器/脚本反复开关串口,主机端
  一旦不排空(端口关闭、脚本崩溃、缓冲积压),设备日志即堵死;用户
  的部分冻结发生在设备插在 Mac 上、而我侧脚本恰好崩溃/占线的时刻。
  拔线反而安全(无主机时 USJ 写直接跳过)。
- **修复**:app_main 最早处 `usb_serial_jtag_vfs_use_nonblocking()`
  ——缓冲满丢字符,永不阻塞(IDF 标准做法)。
- **教训**:① **USB-CDC 控制台 = 与主机的耦合点**,主机故障会拖死
  设备,非阻塞化是嵌入式标配;② 调试期日志洪流(WDT 每 5s 25 行)
  会加速撑爆 CDC 缓冲;③ "设备问题只能靠屏幕现象诊断"的旧结论
  让我们绕了三大圈——**先验证工具假设,再开始排障**。

## 第二十一轮:冻结最终定位(快照法医)+ 自愈兜底

非阻塞 console 上线后用户仍复现冻结("看图→返回列表→加载中长按
确定")。Coroner v2(uxTaskGetSnapshotAll/迭代器版,**只扫当前栈指针
以下的活跃调用链**,无历史残留)在冻结现场拿到决定性快照:
- **全部任务活着且在正常循环**(input/ser_cmd/sys_mon 各自的 yield/
  等待点),**唯独 taskLVGL 的快照内容是空闲任务 prvIdleTask/
  esp_pm_impl_waiti 的调用栈**——屏幕任务的 TCB.pxTopOfStack 指向
  了空闲任务的栈上下文:**TCB/内存被腐蚀**,界面冻结是它的结果。
  (coroner v1 的整段扫描因含历史残留,这一差异此前不可见;
  另:迭代器须全零初始化,置 -1 会导致零遍历。)
- **自愈兜底已部署**:ui_tick(LVGL 任务)每 300ms 心跳;album_watch
  任务(1s)发现"相册前台+屏幕亮+心跳停 10s"即判定冻结,esp_restart
  自愈——**用户侧表现从"永远卡死需拔线"变为"~10s 自动恢复"**。
- 根治路径(后续):腐蚀源在相册直推面板与 LVGL 渲染管线的交互深处
  (async SPI DMA / 驱动内部缓冲/TCB 相邻块),需把相册网格与全屏
  渲染迁移到 LVGL 原生画布(canvas widget)彻底绕开直推,或升级
  esp_lvgl_port 后回归验证。今天先以自愈保可用。
- **教训**:取证工具迭代(快照版)在最后关头才给出干净证据——
  "扫描窗口含残留"的方案输出的是混合信号,差一点把排障引向死路;
  当反复验证的修复都无效时,优先升级证据的精度而不是继续加修复。

## 第二十三轮:终极真因——自动浅睡眠错过唤醒(快照法医 v2 实锤)

Coroner v2(任务快照,只扫当前栈指针以下的活跃链)在冻结现场拿到
决定性证据:**album_task 卡死在 `esp_pm_impl_waiti`(经 xTaskGetTickCount
进入)——任务在浅睡眠中错过了唤醒,一睡 12 分钟,USB 总线一有活动
(我的探针、按键)就被唤醒"自愈"**。这解释了之前所有谜团:
- 冻结后十几分钟"自己好了"= USB 活动唤醒了睡眠中的系统;
- 我侧脚本反复开关串口时高发 = 串口连接状态切换触发浅睡眠进出竞争;
- 面板直推 + 日志洪流是重灾区 = 高频活动加剧竞争;
- 相册任务的 TCB 快照"指向别人的栈" = 读快照时系统正处于半唤醒的
  混乱恢复期,并非真正的 TCB 腐蚀(第二十一轮的腐蚀结论修正)。
- **修复:关闭自动浅睡眠**(esp_pm_configure light_sleep_enable=false,
  DFS 40-160MHz 保留)。代价:待机电流上升,插电无感。
- **教训**:① **电源管理(自动浅睡眠/DFS)是嵌入式"随机冻结"的第一
  嫌疑人**——所有"过会儿自己好了"、"插拔/按键后好了"的现象都指向它;
  ② 排障第一步是 `esp_pm_configure` 的现状检查,而不是应用层。

## 第二十二轮:用户设计的规避——加载中推迟退出(采纳)

用户提出:长按确定时若列表仍在加载则不处理,加载完成后再触发。
采纳并实现(这是规避腐蚀触发窗口的正确姿势,根治迁移前的过渡方案):
- app_album 导出 `album_ui_busy()`:清单拉取中 / 网格页渲染待办或
  进行中 / 在途直推,任一即忙。
- app_registry 长按确定处理:相册前台且 busy → 记入待办
  (s_pending_target=LAUNCHER)+ 提示音,不立即退出;
  input 循环的 process_pending_switch 在忙清零后自动续办;
  switch_to 内 prepare_stop 同步改造:忙时等待(上限 20s,喂 WDT)
  而非打断——等待期间网格正常加载,进度条可见。
- 待办期间后续按键忽略(既有机制)。
- 验证点:加载中长按确定 → 进度条继续走完 → 自动回桌面,全程不冻结。

## 第二十四轮:"看大图返回列表后长按确定没反应,设备崩溃"(串口日志定案)

用户报:相册查看大图返回列表后,再长按确定无法返回,设备直接崩溃。

### 串口取证(/tmp/device_console.log,rc.56 最后一次会话 14:26-16:35)

16:33 唤醒 → OK 进网格(渲染 1.6s ✓)→ OK 看图(拉图+解码静默成功,日志
无失败行)→ OK 返回列表(网格重渲染 1.5s ✓)→ **按下确定并持续按住**:
- +0.8s:`ui_show_status: busy_wait=0ms panel_busy=0`——层级返回正常执行;
- +2.0s:power_hold(1) 弹"继续按住关机\n松开取消"(LVGL overlay);
- **+5.001s(按下时刻差精确 5001ms):`power: Power off: 已关机` → 深睡**,
  USB 随即消失(日志尾 "Device not configured")。

**"崩溃"的真身 = 5 秒长按关机计时器,不是 panic。**按键扫描任务对一次
OK 按住独立计时(2s 提示/5s 关机),完全不管 0.8s 的 LONG 是否已被应用
消费。相册的层级返回(看图→列表→状态页→应用板块)要求逐层长按,而
用户在全机其它界面养成的手势是"长按=返回",于是返回途中持续按住,
5 秒一到设备关机——观感即"没办法返回了 + 直接崩溃"。

次要疑点(未定案,已加取证):ui_show_status 执行成功、album_watch 的
LVGL 心跳全程存活(10s 自愈重启未触发),但 2s 的关机提示 overlay 用户
显然没看见,"返回无可见变化"由此而来——**LVGL 任务活着、刷新通路疑似
哑火**(第 15/17/21/23 轮深层根因的残留形态)。当时的取证手段不足以
定位,本轮补两处探针,复现时直接比对日志。

### 修复

1. **长按关机与本次按住解绑**(本 bug 的直接修复):
   - `app_registry_power_hold_disarm/rearm/is_disarmed`(原子标志);
   - 按键扫描任务在 OK **按下瞬间** rearm;0.8s 的 LONG 被导航消费时
     disarm——消费点共四处:全局拦截三支(WiFi/启动器/应用→启动器)
     + 相册逐层返回(dispatch 分发前);
   - 2s/5s 阶段点读到 disarm 即 `power_stage=2` 静默作废本次按住,
     提示与关机都不再触发。关机手势保留给:**首页**(长按不消费)与
     **熄屏**(熄屏时不置位,2s 提示会唤醒屏幕给予确认)。
   - **时序陷阱:disarm 必须在 on_key 之前置位**——相册状态页长按走
     switch_to→prepare_stop 的最长 20s 等待发生在 on_key 内部,等返回
     再置位的话,扫描任务的 2s/5s 阶段点会先到,慢退出途中按住仍被
     关机(等于顺带修掉"繁忙退出中长按被关机"的第二个坑)。
2. **ui_show_status 取消网格待渲染 + render 入口守卫**:album_task 主
   循环的 mode 是循环顶旧快照,可能在 LVGL 失效恢复**之后**才走进
   render_grid_page,其整屏清黑(无条件、先于逐格守卫)会压掉刚恢复的
   状态屏——"长按返回没反应"的候选机制之一。ui_show_status 现在在
   photo_mutex 内置 `s_grid_render_page = s_grid_page` 关闭渲染待办,
   render_grid_page 入口补模式守卫,旧快照窗口随之关闭。
3. **直推栈缓冲 DMA 屏障补齐**(round-14 纪律收尾):grid_clear_cell
   (26 笔/栈缓冲)、grid_mark_failed、整屏清黑(320 笔)、进度条段
   (静态缓冲逐格重填)四处末尾补 tx_param(0x00) 排空。
4. **取证探针**:ui_show_status 打印 `inv=`(失效开关)/`active=/own=`
   (活动屏归属);ui_tick 每 5s 金丝雀巡检"STATUS 态失效必须常开"——
   哪条路径关了失效没恢复,日志直接点名。
5. 附带:删除 app_registry.cc 冗余的 esp_task_wdt.h include(未使用,
   且 break tests/test_app_registry 的 host 编译——预存损坏)。

### 验证

- `build.sh`:"Project build complete" ✓(亲眼确认,防旧产物陷阱);
- verify_firmware.py:布局 PASS、SRAM 75496/73728 PASS、合并镜像 PASS;
- host 回归全过(Registry/Voice/Xiaozhi/Home/Radio 等;muse 系列因
  /opt/esp-idf 硬编码为本机预存限制,不判)。
- **待烧录后的真机回归点**:①看图→返回→长按确定 0.8s 松手 → 状态屏;
  ②返回后持续按住 5s → 不提示不关机(屏幕停在状态屏);③首页长按 5s
  → "继续按住关机"提示 → 关机;④熄屏状态长按 OK → 亮屏出提示 → 关机;
  ⑤相册加载中长按确定(第二十二轮规避)仍正常延后退出。

### 教训

- **"崩溃"要先验明正身**:本次设备"崩溃"是关机不是 panic——串口日志
  一行 `Power off: 已关机` 加按下时刻差 5001ms 直接定案,免掉一轮盲猜。
- **全局手势与应用内手势共用同一次物理按住时,必须在消费点解绑**:
  "长按返回"与"长按关机"共享一根手指,谁的语义后到谁赢,5s 关机永远
  后到,于是层级返回的持有者必被误杀。
- **慢消费要求 disarm 前置**:消费动作本身可能阻塞(20s 等待),在
  "消费完成"后才解除武装的写法,挡不住武装检查点先到。

## 第二十四轮(续):真凶定案——LVGL 失效计数漂负(串口注入 + 取证日志实锤)

第二十四轮当晚烧录后用串口注入完整复现,新探针当场抓到决定性证据:

    ui_show_status: busy_wait=0ms panel_busy=0   ← 层级返回正常执行
    ui_show_status: inv=0 active==own:true       ← 刚 enable(true) 完读出来仍是关!
    flush delta after long-OK: 0                 ← 长按后 LVGL 一帧都没刷
    canary: invalidation DISABLED while STATUS   ← 6s 后依然关闭

### 真因

**LVGL 9 的 enable_invalidation 是计数制(inv_en_cnt,true/false 各 ±1)**,
而相册的禁用点比恢复点多:一遍"进网格(−1)→看图(−1)→返回(0)"循环计数
**净 −1**,几轮后漂成负数;ui_show_status 的单次 +1 永远凑不回正数,状态屏
从此不再重绘,面板残留旧帧——**"看大图返回列表后长按确定没反应"的真凶**。
且漂移单调向下永不自愈,越用越僵,与"越来越怪"的体感吻合。

之前所有"两个面板写者/代答/TCB 腐蚀"类假设都不成立:面板单写者、锁序、
屏障一直是对的——**死的是一个从未被读过的全局计数**。第二轮发现的首页
分享视图泄漏(开着分享切走,失效不恢复)是同族问题:任何应用都能把计数
关到负,毒死下一个应用的 LVGL 界面。

### 修复(计数夹逼,使计数恒 ∈ {0,1})

1. 相册(app_album.cc):`lvgl_invalidation_off_guarded()`——只在"当前开着"
   时关(1→0,已关则跳过,不再下探);`lvgl_invalidation_on_reset()`——循环
   enable 直到开启(≤0 → 1,有界 10 次)。替换全部 4 个调用点
   (enter_grid_mode/back_to_grid_state/enter_photo_now/ui_show_status)。
   调用方均已持 bsp_lvgl_lock,辅助函数不取锁。
2. 注册表切换点全局复位(app_registry.cc switch_to):旧应用 stop 之后、
   新应用 start 之前,把失效计数夹回开启——任何应用都不能毒死下一个。
   只补到 1,不过度递增。注册表 mock(registry_platform.h)补两个 LVGL
   桩使 host 测试可编译。
3. 同轮还确认:该设备无随身名片,首页分享视图泄漏在本机不会触发;金丝雀
   在整个泄漏路径测试中保持安静。

### 真机验证(串口注入,rc.56+修复)

- 用户手势全链路:看图(静默成功)→返回(网格重渲染 ✓)→长按确定 →
  **inv=1、active==own、ui_show_status 正常执行、panel_flushes 持续增长**
  (修复前同位置 inv=0、flush delta=0);
- 连续两轮"网格→看图→返回→长按"循环,金丝雀全程安静——计数不再漂移;
- 关机解绑(第二十四轮前半)逻辑在 host 回归通过;5s 物理长按行为待用户
  手测(串口无法模拟按住)。

### 教训

- **任何"计数制资源开关"都要夹逼使用,不许散对**:LVGL 的 enable/
  disable、esp_pm_lock、wifi 扫描锁全是这个形状——写第一个 disable 之前
  先问"这个计数会不会被同一路径重复扣减"。恢复点永远无法修复漂负。
- **"开关状态"要纳入日志取证**:一个 `inv=%d` 的单行日志,把三天的排障
  直接钉死。全局可变状态(尤其跨模块的)必须在边界处可观测。
- 串口注入复现时,脚本必须**以日志事件为同步点**(render page done 等),
  固定 sleep 会因网络延迟漂移到错误的模式分支(本轮三次 'L' 打在 PHOTO
  层上,测了个寂寞)。
